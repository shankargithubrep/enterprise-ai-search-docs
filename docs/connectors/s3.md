## Overview

The Elastic S3 Connector synchronises objects from Amazon S3 buckets into Elasticsearch indices using **boto3**, AWS's official Python SDK. It handles content extraction (via Apache Tika), ETag-based change detection, field mapping, and bulk indexing automatically.

In the Enterprise AI-KB architecture, S3 connector instances run as **systemd-managed bare processes** on `m6i.xlarge` connector agent VMs (1 VM per 10–15 tenants). Each instance is scoped to a tenant-specific S3 prefix. Documents flow through the ingest pipeline where Jina v3 embedding is applied before writing to the tenant's Elasticsearch index.

```
S3 Bucket (prefix: tenant-001/)
        │
        ▼
Connector Process (boto3 list + get)
        │
        ▼
Apache Tika (content extraction)
        │
        ▼
Elasticsearch Bulk API  ──►  Ingest Pipeline (Jina v3 embedding)
        │
        ▼
Tenant Index (BM25 + kNN searchable)
```

| Component | Technology | Role |
|---|---|---|
| Connector process | Python 3.10+ / boto3 | Lists objects, fetches content, manages sync state |
| Content extractor | Apache Tika (embedded) | Extracts text from PDF, DOCX, XLSX, HTML and 1,000+ formats |
| Sync state store | `.elastic-connectors` index | ETag snapshot, watermark, last sync timestamp, job status |
| Ingest pipeline | Elasticsearch ingest node | Jina v3 embedding, GeoIP, PII redaction, field transforms |
| Target store | Elasticsearch data stream / index | Tenant-scoped, ECS-normalised, BM25 + kNN searchable |

## How It Works

### Incremental Sync — Step by Step

1. **Schedule trigger** — The connector framework reads the cron schedule from the connector document in `.elastic-connectors`. Default: `0 * * * *` (every hour).

2. **S3 object listing** — boto3 calls `s3.list_objects_v2(Bucket=bucket, Prefix=prefix)` with pagination (1,000 objects per page). All object keys and ETags are collected into an in-memory dict.

3. **ETag comparison** — The connector loads the ETag snapshot from the previous sync stored in the `sync_cursor` field of `.elastic-connectors` and diffs against the current listing:
   - Changed ETag → modified object → re-fetch and re-index
   - In current listing but not in snapshot → new object → fetch and index
   - In snapshot but not in current listing → deleted object → delete from index

4. **Content fetch** — For each new/modified object, boto3 calls `s3.get_object(Bucket=bucket, Key=key)`. The response body stream is passed to Tika.

5. **Tika extraction** — Apache Tika identifies the MIME type and extracts plain text + metadata (author, title, created date). **Hard limit: 10 MB binary input.** Objects exceeding this are silently skipped.

6. **Field mapping** — Extracted text and S3 object metadata are mapped to the Elastic document schema:

   | Elasticsearch field | Source |
   |---|---|
   | `_id` | MD5 hash of the S3 object key |
   | `body` | Tika-extracted plain text |
   | `title` | Tika `dc:title` metadata, fallback to S3 key filename |
   | `url` | `s3://{bucket}/{key}` |
   | `last_modified` | S3 `LastModified` (ISO 8601) |
   | `size` | Object size in bytes |
   | `mime_type` | Tika-detected MIME type |

7. **Bulk indexing** — Documents are batched (default: 100 per batch) and sent to Elasticsearch via `POST /_bulk` with the `pipeline` parameter pointing to the tenant's ingest pipeline. The pipeline runs Jina v3 embedding before writing.

8. **Deletion** — Objects identified as deleted in step 3 are issued as `DELETE` operations in the bulk request.

9. **State update** — On successful completion, the new ETag snapshot and completion timestamp are written back to `.elastic-connectors`. The sync job in `.elastic-connector-sync-jobs` is marked `completed`.

### Full Sync vs Incremental Sync

| | Incremental | Full |
|---|---|---|
| **Trigger** | Cron schedule (default: hourly) | Cron schedule (default: weekly) |
| **ETag snapshot used?** | Yes — only changed/new/deleted objects processed | No — all objects re-fetched and re-indexed |
| **Deletion detection** | Yes — objects in snapshot but not in current listing | Yes — any ES document with no matching S3 key is deleted |
| **Speed** | Fast for low-churn buckets | Scales linearly with object count |
| **Recommended cadence** | `0 * * * *` — every hour | `0 2 * * 0` — Sunday 02:00 UTC |

> **Note:** Full sync is the only reliable mechanism for catching deletions in sources without a native deletion event API. S3 has no change feed, so weekly full sync is not optional — it's the deletion consistency guarantee.

---

### Deletion Detection — The Full Listing Problem

S3 has no native change feed or delta API. Detecting deletions requires the connector to:

1. Maintain a snapshot of all object keys from the previous sync
2. List all current objects in the bucket prefix
3. Diff the two sets

This means **every incremental sync performs a full bucket listing** within the configured prefix. There is no way to ask S3 "what was deleted since timestamp T?".

| Object count | API calls (listing phase) | Estimated listing time |
|---|---|---|
| 5,000 | 5 | ~1–2 seconds |
| 50,000 | 50 | ~10–20 seconds |
| 500,000 | 500 | ~2–5 minutes |

**Implication:** Keep connector prefixes scoped tightly to knowledge base content. Never point a connector at an entire data lake bucket.

### Internal State Machine

The connector maintains state in two system indices:

**`.elastic-connectors`** — one document per connector instance:

```
status: created → needs_configuration → configured → connected → error
```

Key fields: `connector_id`, `service_type`, `index_name`, `configuration`, `scheduling`, `status`, `sync_cursor` (serialised ETag snapshot — critical for change detection), `last_synced`, `last_sync_status`.

**`.elastic-connector-sync-jobs`** — one document per sync job execution:

```
status: pending → in_progress → completed
                             → failed
                             → canceled
```

Key fields: `connector.id`, `job_type` (full/incremental), `started_at`, `completed_at`, `indexed_document_count`, `deleted_document_count`, `indexed_document_volume`, `error`.

Both indices are queryable directly — use `.elastic-connector-sync-jobs` as your primary monitoring source:

```json
GET .elastic-connector-sync-jobs/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "status": "failed" } },
        { "range": { "started_at": { "gte": "now-24h" } } }
      ]
    }
  }
}
```

## When to Use / When Not to Use

| Scenario | Verdict | Reason |
|---|---|---|
| Knowledge base documents (PDF, DOCX, HTML) stored per tenant in S3 | ✅ Use | Exactly the target use case. Tika handles mixed document types automatically. |
| Static content updated infrequently (weekly or less) | ✅ Use | ETag-based incremental sync is highly efficient for low-churn content. |
| Multi-tenant isolation via per-tenant S3 prefixes | ✅ Use | Prefix scoping + per-connector API keys gives clean tenant isolation. |
| Near-real-time availability (<5 min from upload to searchable) | ⚠️ Partial | Set cron to `*/5 * * * *`. Connector is poll-based — no SQS event trigger natively. |
| Buckets with >100K objects under a single prefix | ⚠️ Partial | Full listing becomes slow. Design bucket structure with narrow prefixes. |
| Documents larger than 10 MB | ⚠️ Needs pre-processing | Tika 10 MB limit causes silent skips. Requires pre-ingest chunking pipeline before connector sees the file. |
| Raw log files / append-only event streams in S3 | ❌ Don't use | Use Elastic Agent S3 input or Logstash S3 input instead. Connectors are for documents, not event streams. |
| Password-protected or customer-encrypted documents (SSE-C) | ❌ Don't use | Tika cannot decrypt. Files silently skipped with no alert by default. |
| Versioned S3 bucket — indexing all historical versions | ❌ Don't use | Connector indexes current version only. Requires custom fork for version history. |

## Configuration Reference

### Core Parameters

All configuration is stored in the `.elastic-connectors` system index and can be set via the Kibana Connectors UI or the Connector API.

| Parameter | Type | Default | Description |
|---|---|---|---|
| `bucket` | string | required | S3 bucket name. For this deployment: one bucket per AWS region (e.g. `enterprise-kb-prod-us-east-1`). |
| `prefix` | string | `""` (root) | S3 key prefix. **Must be set for multi-tenant.** Use `tenant-{id}/` per connector instance. |
| `region` | string | `us-east-1` | AWS region of the bucket. Must match the actual bucket region or listing calls fail with a 301 redirect. |
| `aws_access_key_id` | string | blank | Leave blank when using IAM instance profile (recommended). Only set for explicit key auth. |
| `aws_secret_access_key` | secret | blank | Leave blank when using IAM instance profile. Stored encrypted in `.elastic-connectors` if set. |
| `read_timeout` | integer (s) | `90` | boto3 read timeout. Increase to `120` for buckets with large objects. |
| `connect_timeout` | integer (s) | `90` | boto3 connection timeout. |
| `max_pool_connections` | integer | `10` | boto3 connection pool size. Increase to `20` for tenants with high object counts. |
| `use_ssl` | boolean | `true` | Always `true` in production. |
| `verify_certs` | boolean | `true` | Always `true` in production. |

### IAM Policy — Least Privilege

> **Important:** `s3:ListBucket` must be granted on the **bucket ARN**, not the object ARN. `ListBucket` is a bucket-level permission. Without it, listing returns `AccessDenied` and the connector cannot enumerate objects.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "S3ConnectorObjectAccess",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:GetObjectAttributes",
        "s3:GetBucketLocation"
      ],
      "Resource": "arn:aws:s3:::enterprise-kb-prod-us-east-1/tenant-123/*"
    },
    {
      "Sid": "S3ConnectorListAccess",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::enterprise-kb-prod-us-east-1",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["tenant-123/*"]
        }
      }
    }
  ]
}
```

For SSE-KMS encrypted buckets, add:

```json
{
  "Action": ["kms:GenerateDataKey", "kms:Decrypt"],
  "Resource": "arn:aws:kms:{region}:{account-id}:key/{key-id}"
}
```

Python wrapper for bulk provisioning:

```python
from elasticsearch import Elasticsearch

def provision_s3_connector(es: Elasticsearch, tenant_id: str, region: str) -> None:

    key = es.security.create_api_key(
        name=f"s3-connector-{tenant_id}",
        role_descriptors={
            f"connector-{tenant_id}": {
                "indices": [{
                    "names": [f"search-kb-{tenant_id}*"],

    es.connector.put(
        connector_id=f"{tenant_id}-s3",
        body={
            "index_name": f"search-kb-{tenant_id}",
            "service_type": "s3",
            "name": f"Tenant {tenant_id} — S3",
            "configuration": {
                "buckets": {"value": [f"enterprise-kb-prod-{region}"]},
                "prefix":  {"value": f"{tenant_id}/"},
                "region":  {"value": region},
            },
            "scheduling": {
                "incremental": {"enabled": True, "interval": "0 * * * *"},
                "full":        {"enabled": True, "interval": "0 2 * * 0"},
            }
        }
    )
```

## Supported Content Types

| Format | MIME Type | Extraction Quality | Notes |
|---|---|---|---|
| PDF | `application/pdf` | High | Text layer only. Scanned/image PDFs return empty body — requires OCR pre-processing. |
| DOCX | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | High | Full text + embedded metadata. Tables and headers extracted. |
| PPTX | `application/vnd.openxmlformats-officedocument.presentationml.presentation` | High | Slide text + speaker notes. Images not OCR'd. |
| XLSX | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` | Medium | Cell values as flat text. Formulas not evaluated. Complex sheets produce noisy output. |
| HTML | `text/html` | High | Tags stripped, text preserved. JavaScript/CSS not extracted. |
| Plain text / CSV / Markdown | `text/plain`, `text/csv`, `text/markdown` | High | Direct pass-through. No extraction overhead. |
| XML / JSON | `application/xml`, `application/json` | Medium | Values extracted but structure is lost. Consider pre-processing for structured content. |
| ZIP | `application/zip` | Partial | One level of nesting extracted. Inner documents individually extracted. |
| Legacy Office (DOC, XLS, PPT) | `application/msword` etc. | High | OLE2 format supported via Tika POI parser. |
| Images (PNG, JPG, TIFF) | `image/*` | None | No OCR. EXIF metadata only. `body` field will be empty. |
| Password-protected (any format) | varies | None | **Silently skipped. No error written to index.** Monitor via dead-letter pipeline. |

## Known Limitations

| Limitation | Severity | Impact | Mitigation |
|---|---|---|---|
| 10 MB binary content extraction limit | High | Large compliance docs silently skipped. Agents get no results for affected queries. | Pre-ingest chunking pipeline splits docs before connector sees them. Alert on empty `body` field post-extraction. |
| Poll-based only — no SQS/event trigger | Medium | Min latency from S3 upload to searchable = sync interval. | Reduce cron to `*/5 * * * *` for near-real-time. Use Logstash S3+SQS for sub-minute latency. |
| Full bucket listing on every sync | Medium | Sync time scales linearly with object count. 500K objects ≈ 500 API calls in listing phase. | Narrow prefix scoping per tenant. Never point connector at entire data lake bucket. |
| Multipart ETag unreliability | Low | Files uploaded via multipart (>8 MB default threshold) have non-MD5 ETags — spurious re-indexing on unchanged files. | Accept re-indexing overhead. Not a data correctness issue. |
| No S3 object metadata field indexing | Low | Custom `x-amz-meta-*` tags ignored unless explicitly mapped. Metadata-only changes not detected. | Embed metadata in document content or filename. Don't rely on S3 tags for searchable fields. |
| Deletion detection requires full listing | Medium | Deleted objects only caught at full sync (weekly). Stale documents remain searchable up to 7 days. | Run full sync weekly. For immediate deletion: trigger manual full sync via Connector API. |
| Password-protected files silently skipped | High | No error in Elasticsearch. Agents see no results. No default alert. | Add dead-letter index via ingest pipeline `on_failure` handler. |
| Glacier / Deep Archive objects fail on GET | Medium | Objects in Glacier tiers return `InvalidObjectState` error. Connector skips silently. | Ensure knowledge base objects are in S3 Standard or Standard-IA only. Set S3 lifecycle rules accordingly. |
| No connector-level multitenancy management | High | 1,050 connector instances across multi-region require external orchestration. | Ansible-managed systemd units + Kibana sync monitoring dashboard. |
| Modified connector voids Elastic support | High | Any fork of connector source code loses Elastic support for that connector. | Use ingest pipeline processors for custom transformations instead of forking. |

## Enterprise AI-KB Deployment Notes

### Bucket & Prefix Architecture

One bucket per AWS region. One prefix per tenant. One connector instance per tenant scoped to that prefix.

```
enterprise-kb-prod-{aws-region}/
├── tenant-001/
│   ├── faq/
│   │   ├── agent-assist-faq-v3.pdf
│   │   └── product-knowledge-base.docx
│   ├── sop/
│   │   └── escalation-procedures.pdf
│   └── connector-source/
│       └── salesforce-export-2025-01-15.json
├── tenant-002/
│   └── ...
└── tenant-050/
    └── ...
```

- **One connector instance** per tenant → `prefix: tenant-{id}/`
- **One Elasticsearch index** per tenant → `search-kb-tenant-{id}`
- **One API key** per connector with index-scoped write permissions
- **One IAM role** per connector VM with `s3:ListBucket` on the bucket and `s3:GetObject` on the tenant's prefix

### Per-Tenant Provisioning Script

```python
#!/usr/bin/env python3
"""
provision_s3_connector.py
Run at tenant onboarding. Creates connector instance + scoped API key.
"""
import argparse
from elasticsearch import Elasticsearch

REGIONS = [
    "us-east-1", "us-west-2", "eu-west-1", "eu-central-1",
    "ap-southeast-1", "ap-northeast-1",
    # ... remaining 15 regions
]

def provision(tenant_id: str, region: str, es_host: str, admin_key: str) -> dict:
    es = Elasticsearch(f"https://{es_host}:9200", api_key=admin_key)

    # Scoped API key — write access to this tenant's index only
    key_resp = es.security.create_api_key(
        name=f"s3-connector-{tenant_id}",
        role_descriptors={
            f"connector-{tenant_id}": {
                "indices": [{
                    "names": [f"search-kb-{tenant_id}", f"search-kb-{tenant_id}-*"],
                    "privileges": ["write", "create_index", "manage", "read"]
                }]
            }
        }
    )

    # Connector instance
    es.connector.put(
        connector_id=f"{tenant_id}-s3",
        body={
            "index_name":   f"search-kb-{tenant_id}",
            "service_type": "s3",
            "name":         f"Tenant {tenant_id} — S3 ({region})",
            "configuration": {
                "buckets":             {"value": [f"enterprise-kb-prod-{region}"]},
                "prefix":              {"value": f"{tenant_id}/"},
                "region":              {"value": region},
                "read_timeout":        {"value": 120},
                "max_pool_connections":{"value": 20},
            },
            "scheduling": {
                "incremental": {"enabled": True, "interval": "0 * * * *"},
                "full":        {"enabled": True, "interval": "0 2 * * 0"},
            }
        }
    )

    return {
        "tenant_id":    tenant_id,
        "connector_id": f"{tenant_id}-s3",
        "index":        f"search-kb-{tenant_id}",
        "api_key_id":   key_resp["id"],
    }


if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--tenant-id",  required=True)
    parser.add_argument("--region",     required=True, choices=REGIONS)
    parser.add_argument("--es-host",    required=True)
    parser.add_argument("--admin-key",  required=True)
    args = parser.parse_args()
    result = provision(args.tenant_id, args.region, args.es_host, args.admin_key)
    print(result)
```

### Monitoring Skipped Documents

By default the connector produces no signal when Tika skips a document. Add an ingest pipeline `on_failure` handler and a dead-letter index to make skips visible:

```json
PUT _ingest/pipeline/kb-s3-ingest-tenant-123
{
  "processors": [
    {
      "attachment": {
        "field": "_attachment",
        "target_field": "_extracted",
        "indexed_chars": -1,
        "on_failure": [
          {
            "set": {
              "field":  "extraction_failed",
              "value":  true
            }
          },
          {
            "set": {
              "field":  "extraction_error",
              "value":  "{{ _ingest.on_failure_message }}"
            }
          }
        ]
      }
    },
    {
      "inference": {
        "model_id": "enterprise-jina-v3",
        "input_output": [
          { "input_field": "body", "output_field": "body_embedding" }
        ],
        "if": "ctx.extraction_failed == null"
      }
    }
  ],
  "on_failure": [
    {
      "set": {
        "field":  "_index",
        "value":  ".kb-extraction-failures-tenant-123"
      }
    }
  ]
}
```

Query the dead-letter index to see all skipped documents:

```json
GET .kb-extraction-failures-*/_search
{
  "query": { "match_all": {} },
  "_source": ["url", "size", "mime_type", "extraction_error", "@timestamp"],
  "sort": [{ "@timestamp": { "order": "desc" } }]
}
```

Set a Kibana alert when `doc_count` in `.kb-extraction-failures-*` increases by more than 0 in any 1-hour window.

## Technical Q&A

<details>
<summary><strong>How does the connector handle the full bucket listing on every sync — what's the actual API call sequence and memory footprint?</strong></summary>

The connector calls `s3.list_objects_v2(Bucket=bucket, Prefix=prefix, MaxKeys=1000)` and iterates through paginated results using `ContinuationToken`. Each page returns up to 1,000 objects with `Key`, `ETag`, `Size`, `LastModified`, and `StorageClass`.

All `{key: etag}` pairs are accumulated into an in-memory Python dict for the duration of the sync. For a tenant with 5,000 objects that dict is ~5,000 entries × ~200 bytes ≈ **1 MB in memory** — negligible on an `m6i.xlarge` connector VM.

The comparison against the previous ETag snapshot is O(n) dict lookup. The snapshot itself is serialised as JSON in the `sync_cursor` field of the connector document — at 5,000 objects this is ~300 KB of JSON. At 50,000 objects it grows to ~3 MB, still within limits but worth monitoring as bucket contents grow.

</details>

<details>
<summary><strong>What's stored in <code>.elastic-connectors</code> and <code>.elastic-connector-sync-jobs</code>? Can we query them directly?</strong></summary>

Yes, both are standard Elasticsearch indices and fully queryable.

**`.elastic-connectors`** — one document per connector instance:
- `connector_id`, `name`, `service_type`, `index_name`
- `configuration` — all config params as nested object
- `scheduling` — incremental + full cron expressions
- `status` — `created` / `configured` / `connected` / `error`
- `sync_cursor` — serialised ETag snapshot from last completed sync (this is the critical change detection state — losing this means the next sync behaves as a full sync)
- `last_sync_scheduled_at`, `last_synced`, `last_sync_status`

**`.elastic-connector-sync-jobs`** — one document per sync job execution:
- `connector.id`, `job_type` (`full` / `incremental`)
- `status` — `pending` / `in_progress` / `completed` / `failed` / `canceled`
- `started_at`, `completed_at`
- `indexed_document_count`, `deleted_document_count`, `indexed_document_volume` (bytes)
- `error` — error message if `status: failed`

Use `.elastic-connector-sync-jobs` as your **primary monitoring index**. A Kibana lens aggregation on `indexed_document_count` by `connector.id` over 7 days gives you a per-tenant sync health view immediately.

</details>

<details>
<summary><strong>If a sync fails halfway through 5,000 objects after processing 3,000 — what is the exact recovery behaviour?</strong></summary>

Documents already indexed before the failure are **durable** — Elasticsearch acknowledges primary shard writes before responding to the bulk API call, so anything that received a `200` in the bulk response is persisted and not rolled back.

The sync job record is marked `failed`. The `sync_cursor` in `.elastic-connectors` is **not updated** — it retains the ETag snapshot from the last successfully completed sync, not the partial run.

The next scheduled incremental sync will re-compare against the pre-failure baseline and re-fetch all objects whose ETags changed in that run. The 3,000 already-indexed documents will be re-processed but produce no-op updates (same content, same ETag). The 2,000 unprocessed objects will be fetched and indexed. **Net result:** eventual consistency within the next sync cycle, no data loss.

</details>

<details>
<summary><strong>How does the connector handle S3 server-side encryption — SSE-S3, SSE-KMS, and SSE-C?</strong></summary>

**SSE-S3 (AES-256, S3-managed):** Fully transparent. S3 decrypts on `GetObject` automatically if the requester has `s3:GetObject`. No connector configuration needed.

**SSE-KMS (AWS KMS-managed keys):** Transparent if the connector's IAM role has `kms:GenerateDataKey` and `kms:Decrypt` on the relevant KMS key. Without these permissions, `GetObject` returns `AccessDenied` and the object is skipped silently.

**SSE-C (customer-provided keys):** **Not supported.** SSE-C requires the encryption key as an HTTP header on every `GetObject` request. The connector has no mechanism to inject per-request keys. If customers use SSE-C, those objects cannot be indexed by the native connector without a custom fork.

> Recommendation: Use SSE-KMS. Add the KMS permissions to the connector IAM policy.

</details>

<details>
<summary><strong>At 50 tenants with staggered syncs you could still have 6–12 connectors running simultaneously. Could you hit S3 per-prefix rate limits?</strong></summary>

S3's rate limit is **5,500 GET/HEAD per second per prefix partition**. Critically, S3 automatically partitions based on key prefix — if all tenants use `tenant-{id}/`, each tenant prefix is a distinct partition with its own 5,500/s budget.

For an incremental sync of 5,000 objects: ~5 listing calls + ~50 content fetches for changed objects = ~55 GET requests per tenant per sync. At 12 concurrent syncs: **660 GET/s across all prefixes combined**. Well within limits even if S3 treated all prefixes as one partition (it doesn't).

Rate limiting only becomes a concern if you trigger **simultaneous full syncs** of all 50 tenants — that generates ~50,000 GET requests in a short window. Keep full syncs staggered (the weekly schedule already offsets this).

</details>

<details>
<summary><strong>How do you detect silent skips — documents dropped due to the 10 MB limit or password protection — without relying on connector logs?</strong></summary>

Three layers:

1. **Sync job level:** `.elastic-connector-sync-jobs` tracks `indexed_document_count` but not a `skipped_document_count`. Tika-level skips are invisible here.

2. **Ingest pipeline level:** Add a processor that checks if the `body` field is empty after `attachment` processor runs and sets `extraction_failed: true`. Create a Kibana alert on documents with that flag.

3. **Dead-letter index:** Add an `on_failure` handler to the ingest pipeline that routes failed-extraction documents to `.kb-extraction-failures-{tenant_id}`. This gives you the S3 key, file size, MIME type, and error message for every skipped document — actionable for the ops team to trigger manual chunking or re-upload.

See [Monitoring Skipped Documents](#monitoring-skipped-documents) above for the full pipeline configuration.

</details>

<details>
<summary><strong>What happens when the Elasticsearch cluster is unreachable during a scheduled sync — does the connector queue documents locally?</strong></summary>

**No local queue.** The connector has no write-ahead log or local buffer.

If the bulk API call fails (connection refused, `503`, `429`), the connector retries with exponential backoff (default: 3 retries). If all retries are exhausted, the sync job is marked `failed` and that batch of documents is dropped.

Those documents will only be re-processed in the next sync cycle — if their ETag has changed (incremental) or unconditionally (full sync). For a cluster outage during an incremental sync this means up to 1 hour of potential data freshness lag (documents uploaded to S3 in the outage window won't appear until the next successful sync).

This makes cluster availability during sync windows operationally important. The 2-AZ + tiebreaker HA topology and EBS volume health should be proactively monitored.

</details>

**What is NOT automatically mapped:**
- Custom S3 metadata (`x-amz-meta-*` headers) — requires explicit connector config or ingest pipeline field extraction
- S3 object tags (separate from metadata — not available via `GetObject`, requires `GetObjectTagging` call)
- Version ID for versioned buckets — connector only indexes current version, no version field
