## Orchestration Overview

The Elastic connector framework ships the connector process — it does NOT ship fleet orchestration. At production scale (multiple VMs, multiple regions, hundreds of connectors), you need a self-built orchestration layer:

```
Ansible (deployment & config management)
    ↓
systemd (process lifecycle on each VM)
    ↓
Kibana alerting (health monitoring)
    ↓
Runbooks (human-in-the-loop failure recovery)
```

There is no automatic failover in the connector framework. When a VM dies, connectors stop syncing until a human moves them to a healthy VM. The runbook below documents that procedure.

### Playbook

`playbooks/deploy-connectors.yml`

```yaml
---
- name: Deploy Elastic Connector Service
  hosts: connector_vms
  become: true
  roles:
    - elastic-connector
```

`roles/elastic-connector/templates/elastic-connector.service.j2`

```ini
[Unit]
Description=Elastic Connector Service
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User={{ connector_user }}
Group={{ connector_group }}
WorkingDirectory={{ connector_install_dir }}
ExecStart={{ connector_install_dir }}/.venv/bin/python -m connectors.service
Restart=always
RestartSec=30
StartLimitIntervalSec=300
StartLimitBurst=5
StandardOutput=journal
StandardError=journal
SyslogIdentifier=elastic-connector
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths={{ connector_install_dir }}/logs
PrivateTmp=true
Environment=PYTHONUNBUFFERED=1

[Install]
WantedBy=multi-user.target
```

`roles/elastic-connector/tasks/main.yml`

```yaml
---
- name: Install Python and dependencies
  apt:
    name:
      - "{{ python_version }}"
      - "{{ python_version }}-venv"
      - "{{ python_version }}-dev"
      - git
    state: present
    update_cache: true

- name: Create service user
  user:
    name: "{{ connector_user }}"
    system: true
    shell: /usr/sbin/nologin
    create_home: false

- name: Clone connector framework
  git:
    repo: https://github.com/elastic/connectors.git
    dest: "{{ connector_install_dir }}"
    version: "v{{ connector_version }}"
    force: true

- name: Create virtual environment
  command: "{{ python_version }} -m venv {{ connector_install_dir }}/.venv"
  args:
    creates: "{{ connector_install_dir }}/.venv/bin/python"

- name: Install Python dependencies
  pip:
    requirements: "{{ connector_install_dir }}/requirements.txt"
    virtualenv: "{{ connector_install_dir }}/.venv"

- name: Deploy configuration
  template:
    src: config.yml.j2
    dest: "{{ connector_install_dir }}/config.yml"
    owner: "{{ connector_user }}"
    group: "{{ connector_group }}"
    mode: '0600'
  notify: Restart connector service

- name: Deploy systemd service
  template:
    src: elastic-connector.service.j2
    dest: /etc/systemd/system/elastic-connector.service
    mode: '0644'
  notify:
    - Reload systemd
    - Restart connector service

- name: Set ownership
  file:
    path: "{{ connector_install_dir }}"
    owner: "{{ connector_user }}"
    group: "{{ connector_group }}"
    recurse: true

- name: Create logs directory
  file:
    path: "{{ connector_install_dir }}/logs"
    state: directory
    owner: "{{ connector_user }}"
    group: "{{ connector_group }}"
    mode: '0755'

- name: Enable and start service
  systemd:
    name: elastic-connector
    enabled: true
    state: started
    daemon_reload: true
```

`roles/elastic-connector/handlers/main.yml`

```yaml
---
- name: Reload systemd
  systemd:
    daemon_reload: true

- name: Restart connector service
  systemd:
    name: elastic-connector
    state: restarted
```

### Usage

```bash
# Deploy to all VMs in us-east-1
ansible-playbook playbooks/deploy-connectors.yml \
  -i inventory/us-east-1.yml \
  --ask-vault-pass

# Deploy to a single VM
ansible-playbook playbooks/deploy-connectors.yml \
  -i inventory/us-east-1.yml \
  --limit connector-vm-1 \
  --ask-vault-pass

# Dry run (check mode)
ansible-playbook playbooks/deploy-connectors.yml \
  -i inventory/us-east-1.yml \
  --check --diff \
  --ask-vault-pass
```

## Kibana Alerting — Stale Connector Check-In

### Alert Rule Configuration

Create via **Stack Management → Rules → Create Rule**:

| Setting | Value |
|---|---|
| **Rule type** | Elasticsearch query |
| **Name** | Connector Stale Check-In |
| **Index** | `.elastic-connectors` |
| **Query** | See below |
| **Threshold** | `> 0` documents |
| **Check every** | 2 minutes |
| **Notify** | On status change (avoid alert fatigue) |

**Query:**

```json
{
  "bool": {
    "must": [
      {
        "range": {
          "last_seen": {
            "lt": "now-5m"
          }
        }
      },
      {
        "term": {
          "status": "connected"
        }
      }
    ]
  }
}
```

The `status: connected` filter avoids alerting on connectors that are intentionally disabled or in `configured` state (not yet started).

### Slack Webhook Action

Configure a Slack connector in **Stack Management → Connectors → Create Connector → Slack**:

**Message template:**

```
:warning: *Connector Stale Check-In Alert*

A connector has not checked in for 5+ minutes. The connector VM may be down.

*Action required:*
1. SSH to the connector VM
2. Run: `sudo systemctl status elastic-connector`
3. If service is down: `sudo systemctl restart elastic-connector`
4. If VM is unreachable: follow the failover runbook

Check connector status in Kibana: Search → Content → Connectors
```

### PagerDuty Action

For production environments with on-call rotation, configure PagerDuty integration:

| Setting | Value |
|---|---|
| Severity | `warning` (stale > 5 min) or `critical` (stale > 30 min) |
| Dedup key | `connector-stale-{{rule.id}}` |

## Failover Runbook

### Scenario: VM Is Down

**Symptoms:** Kibana stale connector alert fires. VM is unreachable via SSH.

**Impact:** All connectors on the failed VM stop syncing. Search results become stale but remain available (last-synced data is still in the index).

**Recovery steps:**

1. **Identify affected connectors**

   ```json
   GET .elastic-connectors/_search
   {
     "query": {
       "range": { "last_seen": { "lt": "now-10m" } }
     },
     "_source": ["name", "index_name", "last_seen", "service_type"]
   }
   ```

2. **Attempt VM recovery**

   ```bash
   # AWS CLI - check instance status
   aws ec2 describe-instance-status --instance-ids i-0abc123def456

   # Reboot if instance is running but unresponsive
   aws ec2 reboot-instances --instance-ids i-0abc123def456
   ```

3. **If VM is unrecoverable — migrate connectors to a spare or healthy VM**

   a. Copy the failed VM's `config.yml` entries (connector_id + api_key) to a healthy VM's `config.yml`

   b. Add the new connector entries:

   ```yaml
   connectors:
     # ... existing connectors on this VM ...
     # Migrated from failed VM:
     - connector_id: FAILED_VM_CONNECTOR_1
       service_type: sharepoint_online
       api_key: CONNECTOR_1_API_KEY
   ```

   c. Restart the connector service on the healthy VM:

   ```bash
   sudo systemctl restart elastic-connector
   ```

   d. Verify the migrated connectors appear as `connected` in Kibana

4. **Trigger a sync to catch up**

   ```json
   POST _connector/_sync_job
   {
     "id": "MIGRATED_CONNECTOR_ID",
     "job_type": "incremental"
   }
   ```

5. **Post-incident:** Provision a replacement VM and redistribute connectors evenly

**Time to recovery:** 15-30 minutes (manual process).

### Scenario: Connector Process Crash Loop

**Symptoms:** systemd shows `active (running)` but connector keeps restarting. journalctl shows repeated errors.

**Steps:**

```bash
# Check restart count
sudo systemctl show elastic-connector --property=NRestarts

# Check recent errors
sudo journalctl -u elastic-connector --since "10 min ago" -p err

# Common causes:
# 1. Python dependency issue → pip install -r requirements.txt
# 2. config.yml syntax error → yamllint config.yml
# 3. Invalid API key → regenerate in Kibana
# 4. ES cluster unreachable → check network/firewall

# Temporary: increase log level for debugging
sudo sed -i 's/log_level: INFO/log_level: DEBUG/' /opt/elastic-connectors/config.yml
sudo systemctl restart elastic-connector
sudo journalctl -u elastic-connector -f
```

### Scenario: Azure AD Secret Expired

**Symptoms:** Connector shows `error` status. Sync job error: `AADSTS7000215: Invalid client secret provided`.

**Steps:**

1. Generate new client secret in Azure Portal → Azure AD → App registrations → Certificates & secrets
2. Update the connector configuration via Kibana UI (Connectors → [connector] → Configuration → Client Secret)
3. Or via API:

   ```json
   PUT _connector/CONNECTOR_ID/_configuration
   {
     "values": {
       "client_secret": "NEW_CLIENT_SECRET_VALUE"
     }
   }
   ```

4. Trigger a manual sync to verify:

   ```json
   POST _connector/_sync_job
   {
     "id": "CONNECTOR_ID",
     "job_type": "incremental"
   }
   ```

5. Update Ansible vault with the new secret for future deployments

---

### Scenario: Elasticsearch Cluster Unreachable

**Symptoms:** All connectors on a VM show errors. journalctl shows connection refused or timeout errors.

**Steps:**

1. Check cluster health from the VM:

   ```bash
   curl -s https://YOUR_DEPLOYMENT.us-east-2.aws.elastic-cloud.com:443 \
     -H "Authorization: ApiKey YOUR_API_KEY" | jq .
   ```

2. If cluster is down → Elastic Cloud issue, check status page
3. If network issue → check security group rules, VPC peering, DNS resolution
4. If API key expired → regenerate and update config.yml

## Upgrade Procedure

When upgrading the connector framework version (e.g., 9.0.0 → 9.1.0):

1. **Test on one VM first** — never upgrade all VMs simultaneously

2. **Stop the service:**

   ```bash
   sudo systemctl stop elastic-connector
   ```

3. **Update the code:**

   ```bash
   cd /opt/elastic-connectors
   sudo git fetch --tags
   sudo git checkout v9.1.0
   sudo .venv/bin/pip install -r requirements.txt
   ```

4. **Start and verify:**

   ```bash
   sudo systemctl start elastic-connector
   sudo journalctl -u elastic-connector -f  # watch for errors
   ```

5. **Trigger a sync** on one connector to verify

6. **Roll out to remaining VMs** via Ansible:

   ```bash
   ansible-playbook playbooks/deploy-connectors.yml \
     -i inventory/us-east-1.yml \
     -e "connector_version=9.1.0" \
     --ask-vault-pass
   ```

**Rollback:** `git checkout v9.0.0 && pip install -r requirements.txt && systemctl restart elastic-connector`

## Disaster Recovery

### Full Region Failure

If an entire region's connector VMs and Elasticsearch cluster are lost:

1. Provision new VMs from Ansible inventory
2. Deploy connector service via Ansible playbook
3. Connectors will automatically register with the new/restored ES cluster
4. Trigger full sync on all connectors — this rebuilds the indices from source data (SharePoint, Salesforce, etc.)
5. Full sync duration: ~2-4 hours per 10,000 documents per connector (depends on source API throttling)

**Data is not lost** — the source of truth is SharePoint/Salesforce/Confluence. Elasticsearch is a search index, not the primary data store. A full re-sync rebuilds everything.

### Backup Strategy

- **Connector configuration:** Stored in Ansible inventory + vault (version controlled)
- **Elasticsearch indices:** Use Elastic snapshots to S3 for index-level backup
- **Pipeline definitions:** Stored in this documentation repo (version controlled)
- **Azure AD credentials:** Stored in AWS Secrets Manager (or Ansible vault)
